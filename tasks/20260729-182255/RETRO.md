# Retro: Colour the tree by guess closeness

- TASK: 20260729-182255
- DATE: 20260730
- BRANCH: feat/tree-closeness-colour
- OUTCOME: shipped. Guessed species nodes wear the same five closeness tiers the share grid prints. 3 review rounds, verdicts APPROVE -> REQUEST_CHANGES -> APPROVE.

## What went well

**Choosing the data over the renderer paid for itself twice.** Putting the tier on `SpeciesNode.closenessTier` in `buildGuessTree` instead of computing it inside `renderTree` was forced by a constraint that took two minutes to find and would have cost the whole DoD: jest here runs `testEnvironment: "node"` with no jsdom installed, and `jest.config.js` excludes `src/ui/**` from coverage. A tier computed in the renderer could not have been pinned by any unit test, so the "tier parity with the share grid" proof would have had to be a browser test or nothing. Reading the test harness's constraints BEFORE picking where the logic lives turned an untestable design into a plain node-environment test over the real payload, and left the browser to prove only the one thing only a browser can: that the class reaches the DOM and repaints.

**The palette fork went to the user with its constraint named, not just its options.** The flow skill's hardest-won guideline is that offering options without naming the constraint that makes them exclusive leaves the user picking blind. Here the constraint was concrete: mirroring the grid's hues puts tier-3 orange next to the clade amber, and the alternative that dodges it stops matching the emoji the player pastes - which is the entire point of the task. Both options carried their cost in the question, and the accepted one carried its mitigation (the tint fill) into DECISION.md, where the reviewer could check it. The screenshots later showed the mitigation actually works: clade nodes on flat dark, guessed species on a tinted fill, legible even where the hues nearly meet.

**Mutation experiments before commit, not claims.** Both new tests were run against the thing they must reject. The CSS-order experiment produced the exact failure string the spec's comment claims (`all five painted rgb(91, 113, 153)`), so the comment is a recorded observation rather than reasoning. That habit is why the ONE claim that was wrong got caught: it was specific enough to be re-run.

## What went wrong

**The write-up described a different experiment than the one that was run.** The Verification section said the tier-drift mutation was `guessTier(...) - 1`; what was actually run was `Math.max(0, guessTier(...) - 1)`. The clamp is not cosmetic - it collapses tiers 0 and 1 onto the same value, and that collapse is the ONLY reason the ladder test failed. Unclamped, the ladder test passed, because it asserted "five distinct ascending values" and `[-1,0,1,2,3]` satisfies that. So the record overstated the test suite's strength, and the overstatement was invisible from inside the session: the numbers were real, the test names were real, only the mutation string was paraphrased from memory instead of copied from the command that ran. The out-of-context reviewer reproduced the described mutation, got a different answer, and the gap was the finding.

The fix went past the prose to the actual weakness: the ladder test now asserts the tiers ARE `[0..CLOSENESS_TIER_COUNT-1]`, which catches uniform drift and an off-the-end tier that would have no CSS rule.

**A conformance gate was left red and nobody noticed for two rounds.** `DECISION.md` was written with a bare `STATUS: ACCEPTED (user, at the plan gate)` line inside each fork section and no document-level header, so `tatr check` reported `bad-decision-status` and exited 1. AGENTS.md names `tatr check` as a conformance gate to keep clean, and every one of the 13 DECISION.md records already on master carries the `- DATE:` / `- STATUS:` header block. The record was written by pattern-matching what a decision document should SAY rather than by opening a neighbouring one to see what shape the tooling reads. It was present in the round-1 diff and missed by both the round-1 reviewer and this session; only the round-2 pass, which ran `tatr check` on the branch AND on master and diffed the convention across all 13 records, caught it.

## Lessons

- `quote-the-mutation-not-the-memory-of-it` - when recording that an experiment discriminated, paste the mutation VERBATIM from the command that produced the result. Here a paraphrase dropped a `Math.max(0, ...)` clamp, and the clamp was the entire reason the test failed: the described experiment does not reproduce the recorded outcome, and the recorded outcome overstated the suite. A verification claim is only re-runnable if the thing that was run is written down exactly. Sibling of [[a-verification-result-expires-when-the-code-it-ran-against-changes]] - that one is about the result going stale, this one is about the write-up describing code that was never run.
- `assert-the-exact-values-not-a-property-they-happen-to-have` - "five distinct ascending values" and "the values are `[0,1,2,3,4]`" look equally strong and are not: the first is satisfied by `[-1,0,1,2,3]`, so a uniform drift walks straight through it, and the drifted low end has no CSS rule to render with. When a test's job is to pin a fixture to a known scale, assert the scale, not a property of it. Found by the out-of-context reviewer, R1.1.
- `open-a-neighbouring-record-before-writing-a-new-one` - `DECISION.md` was authored from an idea of what a decision record contains, and reddened `tatr check` because the document-level `- STATUS:` line the linter parses lived only inside the fork sections. All 13 existing records had the header. When a repo has a machine-checked artifact convention, the cheapest correct move is to read one existing instance, not to reconstruct the format. Run the repo's own conformance gate (`tatr check`) as part of the work's verification, not only the code gate (`npm run ci`) - they check different things and only one of them was being run.
